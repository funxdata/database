# 02 · 架构设计

## 分层结构

```text
宿主进程 / 其它动态库
        │  直接加载 database 动态库，调用 C 符号（json_in, json_out）
        ▼
┌───────────────────────────────────────────┐
│ src/utils/ffi.rs        导出层（5 个函数） │
│  - 解析 JSON 请求                          │
│  - 校验必填字段                            │
│  - 调用领域方法、包装响应                  │
├───────────────────────────────────────────┤
│ src/utils/cjson.rs      协议层             │
│  - 请求反序列化                            │
│  - 统一响应 {code,data,msg}                │
│  - 写入 1 MiB 上限的 C 缓冲区              │
├───────────────────────────────────────────┤
│ src/db/                领域层              │
│  - FunxDB::open / CRUD / query             │
├───────────────────────────────────────────┤
│ rusqlite + SQLite       存储层             │
│  - 本地数据库文件、WAL                     │
└───────────────────────────────────────────┘
```

> 不存在 HTTP 接入层。`cyctron` 等网关的 HTTP 请求不能调用本库。

## 模块职责

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `src/lib.rs` | crate 根 | `pub mod db/utils`，重导出 FFI 函数；`_force_export` 以取函数地址的方式阻止 `cdylib` 链接阶段裁掉导出符号 |
| `src/db/sqlite.rs` | 连接与关系表操作 | `DATABASE_DIR = "./database"`；`open` 设置 WAL / `synchronous=NORMAL`；`query` 把行转换为 JSON 对象数组 |
| `src/utils/cjson.rs` | 协议编解码 | 请求从 NUL 结尾的 C 字符串解析；响应写回调用方缓冲区，上限 `MAX_JSON_OUT = 1 MiB`；封装 `400/500` 风格业务码 |
| `src/utils/ffi.rs` | 对外接口 | 每个函数重复“解析 → 打开库 → 取字段 → 执行 → 响应”流程；请求结构 `DbReq` 覆盖所有接口字段 |

## 一次调用的完整流程

以 `db_query` 为例：

1. 调用方把 JSON 请求写入 `json_in`，并提供至少 1 MiB 的 `json_out` 缓冲区。
2. `parse_json` 用 `CStr::from_ptr` 读取并以 UTF-8 校验、反序列化为 `DbReq`；失败返回 `400101`。
3. `FunxDB::open(&req.path)`：
   - 创建 `./database/`（如不存在）；
   - 打开 `./database/<path>.db`；
   - 设置 `journal_mode=WAL`、`synchronous=NORMAL`。
4. 校验 `sql` 是否存在，缺失返回 `400104`。
5. `FunxDB::query` 预处理 SQL、读取列名与列类型，逐行构造 `serde_json::Value`。
6. `write_success` 把 `{code:200,data:[...],msg:"success"}` 写入 `json_out`。
7. 函数返回 `c_int`：**表示 JSON 写入结果**（`0` 成功、`-1` 空指针、`-2` 超长），业务成功/失败要看响应体中的 `code`。

> 注意：业务错误（如 SQL 语法错误）同样是“成功写入了错误 JSON”，函数返回 `0`。调用方必须同时检查返回值与 `code` 字段。

## 连接与生命周期

- **每线程连接缓存**：`thread_local` 按数据库路径缓存连接，同一线程重复调用复用；不同线程各自持有连接，不跨线程共享。
- **并发控制**：WAL 支持多读一写；`busy_timeout=5s` 等待锁，写冲突不再立即失败。
- **外键**：连接初始化时开启 `foreign_keys=ON`。
- **无长事务**：关系表 CRUD 均为自动提交，当前没有显式事务接口。

## 错误处理策略

- 底层错误统一转为 `String`（`map_err(|e| e.to_string())`），丢失了 SQLite 错误码/错误种类，无法区分“约束冲突”“语法错误”“磁盘满”等。
- 导出层把错误映射为固定业务码：
  - `400101` JSON 解析失败
  - `400102` 缺少 `table`
  - `400103` 缺少 `schema`
  - `400104` 缺少 `sql`
  - `500100` 打开数据库失败
  - `500101` SQL 执行失败
- 码值集中定义在 `src/utils/errors.rs`，不再散落在各函数中。

## 设计取舍

| 取舍 | 现状 | 影响 |
| --- | --- | --- |
| 传完整 SQL 而非结构化参数 | SQL 仅由调用方 lib 内部发起 | 接口简单；不提供参数绑定 |
| 每线程连接缓存 | 有状态 | 复用连接提升吞吐；跨线程不共享 |
| 固定 1 MiB 输出 | 简单 C ABI | 当前业务输入/输出与分页均不会超过 |
| `cdylib` + `rlib` | 动态库交付，rlib 供测试 | 可被宿主加载，也可运行 Rust 测试 |
| 仅库文件调用 | 无 HTTP 接入 | 只能由能加载动态库的进程使用 |
| 表名白名单 + 引号 | 受信任 schema | 兼容保留字，拒绝非法标识符 |
